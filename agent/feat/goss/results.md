# Forust GOSS Results

Date: 2026-10-06. Branch: `feat/goss`. Machine: 8 physical cores (16 vCPU), 62 GB.
Raw records: `results.jsonl` (generated by `scripts/perf_goss.py run`; tables by
`scripts/perf_goss.py report`).

## Summary

- **Baseline:** random row sampling with `subsample=0.8` (`random80`). No sampling
  (`none`) is shown for information.
- **Speed:** on 1M x 200 at 8 threads, a 100-iteration fit with default GOSS
  (`top_rate=0.2`, `other_rate=0.1`) takes 15.35 s versus 24.10 s for `random80`,
  **1.57x faster** (target 1.5x, pass). Across datasets GOSS is 1.39-1.86x faster.
- **Accuracy, fixed 100 iterations:** GOSS is within -0.55% to +0.19% of the
  baseline's eval logloss on every dataset (pass).
- **Accuracy, early stopping:** GOSS is +0.98% (w200 100k, pass), -0.11% (w500
  100k, pass), and **+1.63% (w200 250k, fail)**. LightGBM's GOSS loses a similar
  amount against LightGBM bagging on the same data (+1.38%, +0.25%, +1.35%).
- **GOSS versus random sampling with the same row budget (`random30`):** at a fixed
  100 iterations, `random30` is as fast and slightly better, because neither model
  has converged and smaller samples regularise. Under early stopping, GOSS is
  clearly better on w200 100k (+0.98% vs +4.58%) and w500 (-0.11% vs +4.01%), and
  tied on w200 250k (+1.63% vs +1.54%).
- **`goss-small` (0.1/0.1) is not recommended:** up to +10% logloss under early stopping.
- **Forust versus LightGBM GOSS:** similar accuracy; LightGBM trains faster
  (its fit excludes dataset construction, shown as the gap between Total and Train).

## Optimisations measured with `perf_phases` (1M x 200, 8 threads, steady state per tree)

| Version | Tree | Row selection | Subset copy | Total |
| --- | ---: | ---: | ---: | ---: |
| No sampling | 220.5 ms | - | - | 220.5 ms |
| GOSS, serial selection, no subset | 111.1 ms | 17.6 ms | - | 128.7 ms |
| + contiguous row subset | 89.2 ms | 15.2 ms | 11.6 ms | 116.0 ms |
| + parallel block selection | 85.5 ms | 4.8 ms | 11.1 ms | 101.4 ms |

The subset copy reads almost the whole binned matrix, so it is bandwidth-bound.
Subset trees are byte-identical to full-data trees (unit tested); block selection
gives identical models with `parallel` on or off.

## Caveats

- **The 1,000-tree cap was usually reached.** With learning rate 0.1 most
  "early stopping" runs stopped at or near 1,000 trees, so they are closer to
  1,000 fixed iterations than to converged models. The w200 250k failure is in
  this regime. A larger cap or a higher learning rate would test convergence properly.
- **Runs stopped early by request:** the 1M early-stopping comparison (only 2
  `random80` runs finished, no GOSS), the 1-thread check, and the per-tree
  `perf_sweep` runs were not completed. The 1M early-stopping table is omitted.
- Totals include each library's dataset construction. XGBoost's DMatrix doesn't bin,
  so its Train column is the comparable figure.
- Synthetic data only (`make_perf_data.py`, seed 0); sampled settings use seeds 0-4.
