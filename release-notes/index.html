    Performance Release Notes

    Scope

    This page preserves the results and reasoning from the performance work recorded in October 2026. The original working notes and raw JSONL benchmark output were kept under agent/ while the work was in progress. They are now summarized here so the repository keeps the durable conclusions without carrying a temporary experiment archive.

    The measurements were taken on an Azure VM with 8 physical cores, 16 vCPUs, and 62 GB of RAM. Unless noted otherwise, runs used release builds, 8 threads, synthetic data generated by scripts/make_perf_data.py with seed 0, 256 bins, learning rate 0.1, depth 5, and one evaluation set. Timings vary by roughly 5-10% between runs.

    Executive Summary

    The main bottleneck was tree construction, not prediction or evaluation. In the original 1,000-iteration workload with 100,000 rows and 200 columns, tree building accounted for 93.3% of total time. The optimization work moved the largest serial sections into parallel execution, reduced repeated allocations and copies, and made binning parallel.

    The recorded end-to-end results were:

    Workload Before After Result
    100 iterations, 1M x 200, 8 threads 52.7 s 26.1 s 2.0x faster
    1,000 iterations, 100k x 200, default threads 80.8 s 37.2 s 2.2x faster
    Tree time, 8 threads, 25k-250k rows baseline -39% to -81% substantially lower
    Binning, 8 threads, 1M x 200 24.7 s 1.8 s 91-93% less
    8-thread speedup over serial 1.0-3.1x 4.6-5.2x much better scaling

    Every kept change was checked for byte-identical model output. The recorded Python test suite passed with 112 tests during the main optimization work and 121 tests during the histogram follow-up.

    Tree-Building Optimizations

    The following changes were measured and kept:

    Change Recorded effect
    Parallel split search 17-38% faster at 8 threads
    Borrow gradients instead of copying 3-10% faster
    Write histograms in place 15-33% faster at 8 threads
    Parallel histogram subtraction Up to 28% faster at 8 threads
    Parallel binning with one sort per column Binning 11-14x faster
    Configurable num_threads Makes thread-count tuning explicit
    Run parallel work on a pool thread 4-40% faster at 8 threads

    The analysis found that histogram accumulation was only part of the problem. Split search, histogram subtraction, gradient/Hessian gathering, per-column histogram assembly, and row partitioning remained serial and dominated smaller or deeper trees. Parallelizing independent feature scans and per-column work improved scaling while preserving the existing tie-breaking behavior.

    The recommended setting on the benchmark host was 8 threads, one per physical core. The default 16 threads was 2-18% slower at depth 5 and 25-66% slower at depth 8. This is workload and machine dependent; applications should measure on their own hosts before changing thread settings.

    Histogram follow-up

    Two additional changes were kept:

    • Skip histogram construction for children at max_depth, reducing tree time by 10-35% in the measured cases.
    • Remove the redundant cut_value field from Bin, reducing tree time by up to 21% on small nodes and deep trees.

    The combined before/after measurements were:

    Data Rows Setting Before After Change
    w200 100k none 3.47 s 2.49 s -28.1%
    w200 100k random80 3.21 s 2.30 s -28.3%
    w200 100k GOSS 2.31 s 1.94 s -16.0%
    w200 250k none 7.91 s 5.60 s -29.2%
    w200 250k random80 7.13 s 5.18 s -27.4%
    w200 250k GOSS 4.42 s 3.46 s -21.7%
    w500 100k none 7.92 s 5.76 s -27.3%
    w500 100k random80 7.20 s 4.98 s -30.9%
    w500 100k GOSS 4.88 s 3.57 s -26.8%
    w200-1m 1M none 26.74 s 19.53 s -27.0%
    w200-1m 1M random80 24.10 s 18.35 s -23.8%
    w200-1m 1M GOSS 15.35 s 12.92 s -15.8%

    These are median total fit times for 100 iterations with one evaluation set. Evaluation logloss was identical before and after for these comparisons.

    GOSS Sampling

    Forust now supports Gradient-based One-Side Sampling (GOSS), following the LightGBM approach. GOSS keeps the rows with the largest gradients and samples from the remaining rows, scaling the retained small-gradient rows to keep split statistics close to unbiased. With the default top_rate=0.2 and other_rate=0.1, the first int(1 / learning_rate) trees use all rows as a warm-up.

    Against random 80% row sampling (random80), fixed 100-iteration runs showed:

    Data random80 GOSS Speedup
    w200, 100k 3.21 s 2.31 s 1.39x
    w200, 250k 7.13 s 4.42 s 1.61x
    w500, 100k 7.20 s 4.88 s 1.48x
    w200-1m, 1M 24.10 s 15.35 s 1.57x

    Across these datasets, fixed-iteration GOSS logloss was within -0.55% to +0.19% of the random80 baseline. Early stopping was within +0.98% on w200 100k and -0.11% on w500 100k, but was +1.63% worse on w200 250k. That last case exceeded the recorded 1% tolerance and is an important caveat rather than a result to hide. The early-stopping runs usually reached the 1,000-tree cap, so they were not all fully converged comparisons.

    GOSS-specific implementation measurements on 1M x 200 were:

    Configuration Tree Row selection Subset copy Total
    No sampling 220.5 ms - - 220.5 ms
    GOSS, serial selection 111.1 ms 17.6 ms - 128.7 ms
    GOSS plus contiguous row subset 89.2 ms 15.2 ms 11.6 ms 116.0 ms
    GOSS plus parallel block selection 85.5 ms 4.8 ms 11.1 ms 101.4 ms

    The subset tree output was byte-identical to the full-data tree output in the recorded checks. Parallel and serial GOSS block selection also produced identical models.

    Experiments That Were Not Kept

    Several ideas were measured and rejected, and recording those results prevents repeating the same investigations:

    • Reusing histogram buffers was slower at depth 5: about 6% slower at 250k rows and 7% slower at 1M rows.
    • Reusing the per-column sums buffer was 6-30% slower in the tested cases.
    • u8 bins were 7-20% faster in the histogram-fill microbenchmark, but only apply when all columns fit within 255 bins. The default 256-bin layout needs u16, and the required generic plumbing was not justified by the measured end-to-end gain.
    • u32 row indices showed no useful microbenchmark gain.
    • Building small nodes serially was slower at every tested threshold.
    • A faster weighted pair sort gained about 2% but carried a small risk of changing last-digit cut values.

    The remaining likely bottlenecks are row partitioning after each split, split evaluation for every bin, histogram accumulation and Rayon scheduling for many small deep-tree nodes. These are candidates for future profiling, not claims of completed work.

    Reproducing the Measurements

    Synthetic datasets can be regenerated with:

    python scripts/make_perf_data.py --out /tmp/forust-perf/w200 --rows 250000 --eval-rows 62500 --cols 200
python scripts/make_perf_data.py --out /tmp/forust-perf/w500 --rows 100000 --eval-rows 25000 --cols 500
python scripts/make_perf_data.py --out /tmp/forust-perf/w200-1m --rows 1000000 --eval-rows 250000 --cols 200

    The benchmark helpers are kept under scripts/. Their generated result files default to ignored target/perf/, while the larger datasets and golden files use /tmp/forust-perf/. The main tools are:

    • perf_sweep.py for steady-state tree timing and thread scaling.
    • perf_grid.py for repeatable before/after grids.
    • perf_compare.py for markdown comparisons between labels.
    • perf_golden.py for byte-identical tree checks.
    • perf_goss.py for GOSS accuracy and speed checks.
    • perf_reference.py and perf_xgboost.py for external reference timings.
    • perf_serial_share.py for Linux perf sampling of serial work.

    These numbers are historical engineering measurements, not a promise of a fixed speedup for every dataset or machine. Hardware, feature cardinality, tree depth, sampling, thread count, and evaluation frequency all affect the result.
